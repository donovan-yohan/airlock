Security model

Assume the model-facing side is compromised.

Airlock is useful only if the requester node cannot turn text, state, or transport access into trusted execution. The integration is designed around that assumption.

Threat model

Untrusted by location, content, and intent

The harness, skill text, MCP process, requester service, profile labels, reasons, argv, and model-generated fields all live on or originate from the untrusted side. Signed catalog metadata proves origin and integrity; it does not turn descriptive text into instructions.

Core rule: model-visible text can request authority. It can never grant authority.

Model-facing surface

Exactly three tools

  • airlock_capabilities
    Discover the signed github.command/v1 profile, labels, and argv limits.
  • airlock_create_request
    Submit exact ordered gh argv and a bounded reason. This does not execute it.
  • airlock_requests
    Read sanitized proposal and receipt state without trusted paths, output, or reusable approvals.

Proposed argv is model-visible because it is the request. There are no hooks, provider clients, shell interpreters, trusted-node URLs, secret headers, output fields, or direct execution methods in the model surface. shell.run/v1 is reserved but disabled.

Requester transport

Loopback, explicit, and boring

  • Requester URLs must be explicit http://127.0.0.1:<port> values.
  • Credentials, URL user-info, query strings, fragments, redirects, and inherited proxies are refused.
  • The MCP server can advertise tools while the requester is offline, but returns sanitized unavailable errors for live operations.
  • The requester never connects directly to an external provider on the agent's behalf.

Trusted side

Resolve authority locally

The trusted node pulls hostile proposals and verifies the signed catalog context, canonical digest, expiry, profile/version, argv bounds, and idempotent request identity. Request IDs cannot be reused with different bytes.

Only then does it resolve a plan from trusted-local configuration: absolute GitHub CLI path and SHA-256 identity, exact proposed argv, authority/identity/sandbox/network/cwd/output labels, config version, fixed environment, and bounded timeout. The plan digest and plan persist before invocation. No shell or PATH lookup occurs; shell metacharacters remain argv data.

Each Linux child runs in Bubblewrap with only its pinned static gh, private work directory, read-only minimal hosts.yml snapshot, and CA/DNS runtime data. It inherits no ambient HOME/token/proxy variables. Stdout/stderr previews are separately bounded, sanitized, and credential-redacted for trusted review only; they never cross to requester/MCP/Hermes, receipts, or ordinary logs. Network, including host loopback, remains shared, so this is not an egress firewall or a semantic-safety claim.

Linux local control uses an owner-private Unix socket and verifies SO_PEERCRED for every accepted connection before HTTP reads it. The peer UID must equal the daemon's effective UID; filesystem modes are defense-in-depth, not an authentication substitute. Unsupported platforms fail closed instead of exposing this control plane without peer credentials.

Human boundary

One trusted human approval before pinned execution

  1. Decision: inspect request and plan digests, every argv element, local policy labels, and risk warnings, then approve that exact plan or deny.
  2. Attempt: Airlock persists approval plus a running reservation, then executes outside its store lock. Failures are bounded and retries are explicit.

Requester/MCP/Hermes surfaces do not bridge this action. There is no edit path: deny and resubmit. Risk warnings are reviewer assistance, not an operation allowlist. An approved broad credentialed command is reviewer-approved RCE. See the approval timing diagram for the full sequence.

Installer integrity

Fail closed around user-owned files

  • The binary source must be an explicit executable and is installed content-addressably.
  • Only exact airlock@airlock plugin identity is considered installer-owned.
  • Instruction blocks require both managed markers and matching path/digest state.
  • Unrecorded, edited, malformed, missing, or symlinked instruction targets are refused.
  • A failed Hermes config read aborts before plugin, MCP, file, or ownership state removal.
  • Default install and update do not read or back up global instruction files.

Evidence semantics

Receipts describe workflow state, not external truth

approved_for_execution proves a trusted reviewer reserved one exact plan digest. executed proves only that the trusted child returned success and its completion persisted. It does not prove provider state: whether the provider accepted the action or the intended state exists.

Every success claim therefore ends with an independent ordinary read-only verification path.
